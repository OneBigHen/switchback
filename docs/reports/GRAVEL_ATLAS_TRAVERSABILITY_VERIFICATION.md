# Gravel Atlas traversability verification

Branch: `feat/pa-gravel-atlas-routing`
Activation scope: **NJ only** (`njgin-ng911`); Pennsylvania remains authorization-gated.

## Current release contract — policy v2

The runtime Atlas must be generated by the current end-to-end verifier, identified by
`GRAVEL_ATLAS_TRAVERSABILITY_POLICY_VERSION = 2`. Runtime databases use schema version 2
and persist that verifier-policy identity alongside the source and routing-graph
fingerprints. Evidence produced under an older verifier policy is intentionally stale and
must not be served as current routing evidence even when its source and graph fingerprints
still match.

`npm run gravel-atlas:verify-routability` asks the running GraphHopper service to route
each reconciled corridor from end to end and independently measures whether the returned
route actually follows that corridor. A corridor is published as `routable` only when all
of these policy-v2 conditions hold:

- GraphHopper returns a non-degenerate endpoint-to-endpoint route;
- both corridor endpoints snap to the routable network within **60 m**;
- matching uses a **20 m** corridor/route radius;
- at least **80%** of corridor samples match within that radius *and* satisfy local
  direction agreement;
- one continuous matching run covers at least **60%** of the corridor;
- at least **85%** of proximity hits agree with the corridor's local direction; and
- route distance is no more than **1.5x** the corridor distance.

Any missing or invalid measurement fails closed. Refused corridors are quarantined with
the measured reason and metrics. `gravel-atlas:refresh:nj` runs source staging, graph
reconciliation, policy-v2 traversability verification, and only then runtime publication.
The runtime builder accepts the traversability-filtered artifact and rejects stale policy
versions.

## Why the live-router step exists

The canonical exporter proves corridor membership **per OSM segment**: each retained
canonical segment is checked against the hard motorcycle access and one-way rules used
for the GraphHopper import. That is not the same question as "can the built graph carry
this corridor end to end", because snapping, subnetwork handling and profile weighting
act on the complete path.

A live diagnostic run on September 11, 2026 demonstrated this gap. The clearest example
was Georgia Okeefe Way: a 702 m corridor whose underlying way was present and legally
open, and whose samples snapped within 1–6 m, while endpoint routing returned a 3597 m
route (about 5.1x the corridor). Segment-only verification could not detect that
contradiction.

## Required policy-v2 release evidence

The next activation report must come from a fresh `gravel-atlas:refresh:nj` run on the
exact release head. Record, rather than infer, all of the following:

- traversability policy version and runtime schema version;
- source, source-snapshot, and routing-graph fingerprints;
- source fetched / accepted / rejected / duplicate counts;
- canonical graph-segment count and reconciled-corridor count;
- policy-v2 published and refused corridor counts;
- quarantine totals grouped by reason;
- accepted-corridor aligned coverage: minimum, p5, median, and mean;
- minimum accepted continuous-coverage fraction;
- minimum accepted direction-agreement fraction;
- maximum accepted detour ratio;
- worst accepted endpoint snap; and
- representative OFF / Balanced / More / Maximum and Free Ride results using corridors
  actually present in the newly generated runtime database.

If the current verifier rejects materially more corridors, investigate the specific
geometry/router evidence. Do not weaken the thresholds merely to recover the historical
38-corridor count.

## Reproducing the current gate

```bash
npm run routing:fingerprint
npm run gravel-atlas:refresh:nj

# Optional standalone verifier pass against the reconciliation output
npm run gravel-atlas:verify-routability -- \
  --input=data/gravel-atlas-verified.json \
  --out=data/gravel-atlas-verified-traversable.json \
  --report=data/gravel-atlas-traversability.json
```

The runtime build must consume `data/gravel-atlas-verified-traversable.json`. Generated
SQLite, graph, PBF, verification JSON, and report artifacts are build/runtime products and
must not be committed.
